# 한 줄 때문에 바퀴가 안 죽게 · 상세를 덜 두드리게 (2026-10-14 세중님 0·1번)

## 0. 한 줄 때문에 바퀴가 통째로 죽지 않게

### 무슨 일이 있었나

```
22:00  ok=false · 담음 0
       400 22P05 unsupported Unicode escape sequence
           \u0000 cannot be converted to text
21:00  ok=true · 담음 276        ← 고치기 전
```

제가 그날 「담을 것은 전부 상세를 엽니다」로 넓히면서 상세를 167건 더 열었고,
**NUL(`\u0000`)이 든 본문**을 처음 만났습니다. PostgreSQL 의 `text` 가 그걸
못 받습니다. **한 건이 그 바퀴 전체를 죽였습니다** — 200줄씩 한 번에 보내기
때문입니다.

글자를 걷는 고침은 따로 했지만 그것은 **아는 꼴 하나**만 막습니다.
모르는 꼴이 또 오면 똑같이 죽습니다. 그래서 **구조로** 막았습니다.

### 어떻게

`tools/보낼줄.mjs` **한 자리**입니다.

```
① 보내기 전에 줄마다 봅니다      제어 글자 · 길이 · 객체인지
② 묶음이 실패하면 반씩 나눕니다   문제 줄만 가립니다
③ 뺀 줄은 셈과 까닭을 남깁니다    조용히 버리지 않습니다 (지침 2절)
```

16줄 중 한 줄이 나쁠 때 창구를 **9번** 부릅니다 (한 줄씩이면 16번).

`collect-hosp.mjs` 의 세 자리가 모두 이 길로 갑니다 —
`collect_put` · `collect_trash` · `collect_body`.
**22:00 에 죽은 자리는 `collect_body`** 였습니다.

### 남기는 길

```
수집기 → 박동 메모(못담음 · 못담은것)
      → 담지못한줄() 창구
      → hold_digest
      → 아침 메일 「담지 못한 줄 N건」 · 15시 메일 「██ 수집기가 창구에 못 보낸 줄 ██」
```

**0 이 정상입니다.**

### 시험 (세중님이 시키신 그대로)

`--나쁜줄시험` 깃발로 **NUL 이 든 가짜 줄 하나를 한가운데** 섞어 실제로
한 바퀴 돌렸습니다. 그 줄은 보내기 전에 걸러져 창구에 안 갑니다 —
되돌릴 필요가 없는 쪽으로 짰습니다 (지침 8-9).

```
★ --나쁜줄시험 — NUL 이 든 가짜 줄 하나를 섞었습니다 (TEST나쁜줄)
씀          274건
  ⚠ 담지 못한 줄 1건 (collect_body) — 나머지는 담았습니다
원문 보관    162건
남은 프로세스 0
```

박동에 남은 것 —
```json
{"id": "TEST나쁜줄", "어디": "collect_body",
 "까닭": "못 쓰는 글자 U+0000 (칸 body · 1번째)"}
```

**고치기 전이라면 담음 0 이었을 것입니다.**

자기점검 **15가지** (`node tools/보낼줄.mjs`). 첫 판은 못 담은 줄이
「(id 없음)」으로 남았습니다 — `collect_body` 는 `id` 가 아니라 `job_id` 를
씁니다. `줄이름()` 을 한 자리에 두어 고쳤습니다.

## 1. 상세 여는 횟수 줄이기

### 왜

「담을 것은 전부」로 넓히니 한 바퀴에 **168번**, 크론이 `0 7-22`(하루 16바퀴)라
하루 약 **2,688번** 병원 사이트를 두드리게 됐습니다. 부담도 부담이고
차단 위험이 있습니다.

### 규칙 (세중님)

```
매 바퀴 여는 것   처음 본 공고 · 본문이 비었거나 메뉴뿐인 공고
하루 한 번만      이미 쓸 만한 본문을 받은 공고 (20시간 · 바퀴가 밀려도 되게)
사이트당 뚜껑     50 그대로
```

**「쓸 만한」을 글자 수로 가르지 않습니다.** 그러면 왼쪽 메뉴가 「원문 있음」이
됩니다 — 2026-10-14 에 `length(body) > 200` 으로 재서 17건을 그렇게 셀
뻔했습니다 (지침 15절). **본문에 「치료사」가 있는지**를 봅니다.
「직군 의심」 그물과 **같은 잣대**입니다 (지침 6절).

판정은 DB 의 `상세건너뛸공고()` **한 자리**입니다.

### 전후

```
전   상세 연 것 168건/바퀴   하루 16바퀴 × 168 ≈ 2,688번
후   상세 연 것 128건/바퀴   하루 16바퀴 × 128 ≈ 2,048번   (−24%)
     (담을 것 167건 중 41건은 오늘 이미 받아서 건너뜁니다)
```

목록 받기는 그대로입니다 — 304곳 × 16바퀴 ≈ 4,864번.

**왜 더 안 줄었나** — 담을 것 167건 중 **126건이 본문이 비었거나 메뉴뿐**이라
세중님 규칙대로 매 바퀴 열어야 합니다. 그 수가 줄어야 요청도 줍니다 —
㉮·㉯ 가 풀어야 할 바로 그 문제입니다. 병원 게시판 본문이 메뉴뿐인 곳이
그만큼 많습니다.

### ★ 돌려 보고 잡은 것

처음 판은 **id 만** 건너뛸 목록에 넣었습니다. 그랬더니 **회원 화면이 39 → 34**
로 줄었습니다. 상세를 건너뛴 공고의 **직군이 매 바퀴 다시 사라져** 보류함으로
갔습니다 — 그 직군은 상세 본문에서 가린 것이라, 상세를 안 열면 수집기가
「직군 못 가림」으로 봅니다.

→ `상세건너뛸공고()` 가 **그때 가린 직군을 함께** 돌려줍니다. 수집기가
그대로 이어받습니다 (한 바퀴에 5건). **회원 39 로 돌아왔습니다.**

돌려봐야 알았습니다 (지침 12절).

### 아직 안 한 것

세중님 글의 「정찰과 겹치면 정찰에 맡기기」는 아직 안 했습니다.
정찰은 02:15 에 돕니다. 겹치는 자리를 보고 나서 붙이겠습니다.

## 4. 「메뉴뿐인 본문」 쪼개 보기 (2026-10-14 밤 · 읽기만)

### ★ 제가 쓴 「126건」이라는 이름표가 틀렸습니다

어제 보고에 「담을 것 167 중 **126건이 본문이 메뉴뿐**」이라고 적었습니다.
그 126은 **「건너뛸 수 없어서 매 바퀴 여는 수」**이고, 그 대부분은
**보류함 공고**입니다 — 간호사·행정 공고라 본문에 「치료사」가 없는 것이
**당연합니다.** 메뉴뿐이어서가 아닙니다.

제대로 세려면 **공고말(접수기간·지원자격 …)이 있는지**를 봐야 합니다.

```
HS3 본문 120건 (숨긴 것 빼고) —
  ㉮ 메뉴뿐 (공고말 없음 · 문장부호 25 미만)   36건 / 20기관
  ㉯ 공고말이 없음 (다른 직군 공고일 수 있음)   17건 / 13기관
  ㉰ 공고 본문이 있음                        67건 / 40기관
```

**진짜 「본문 못 받아옴」은 36건입니다.**

함께 풀립니다.** 2번에서 첨부 주소도 같은 계열로 풀었습니다.
