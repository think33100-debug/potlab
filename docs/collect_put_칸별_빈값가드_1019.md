# `collect_put` 칸별 빈 값 가드 — 24칸 전체 (2026-10-19)

세중님 ② — 「같은 꼴로 `apply_to_time`·`apply_from` 등 다른 날짜 칸도 빠진 게
없는지 **24칸 전체 다시 훑고 표로**(칸 · 가드 있음/없음 · 까닭). 남겨둘
칸(`title`·`org_name` 등)은 **「null 이 정말로 '기관이 지웠다'일 수 있는지」
근거 한 줄씩**.」

## 0. 「가드」가 무엇인가

`collect_put` 의 `on conflict do update` 에서 **수집기가 보낸 값이 null 일 때
기존 값을 지키는 줄**입니다.

```sql
when excluded.<칸> is null then j.<칸>      -- 이 한 줄이 가드입니다
```

**새 값이 있으면 그대로 덮습니다** — 그러니 기관이 값을 바꾸면 따라갑니다.
가드는 「못 읽어서 null」만 막습니다.

## 3. 「null 이 정말로 '기관이 지웠다'일 수 있나」 — 칸마다

세중님이 물으신 핵심입니다. **지금까지 이 물음에 「그럴 수 있다」고 답할 수
있는 칸은 둘뿐입니다.**

```
job_group   ○ 있습니다 — 재판정으로 「우리 직군 아님」이 될 수 있습니다.
              그래서 가드를 넣지 않고, 대신 상세를 건너뛸 때 **그때 가린
              직군을 이어받습니다**. 이쪽이 맞는 길입니다
evidence    ○ 있습니다 — 우리가 쓴 판정 근거이고 매 바퀴 새로 써야 합니다

apply_to    ✗ **아닙니다.** 기관이 마감일을 지우고 「채용완료시까지」로 바꾸는
              일은 있지만, 그때는 **원문에 그 말이 들어옵니다** — 수집기가
              null 을 보내는 것과 구별됩니다. 2026-10-19 에 실제로 재 보니
              지워진 5건 전부 **원문에 날짜가 그대로 있었습니다**
apply_from  ✗ 같습니다
headcount   ✗ 2026-10-18 에 확인 — 되메우기가 채운 4건의 원문에 인원이
              그대로 있었습니다
work_place  ✗ 같은 자리 (2026-10-18)
sido · sgg  ✗ **우리가 계산하는 값**입니다. 기관이 지울 수 있는 것이 아닙니다
form · org_kind ✗ 같습니다 — 우리 계산
hire_type · employ_type · edu · posted_at  ✗ 상세·목록에서 읽는 값이고,
              기관이 공고에서 그 줄을 지우는 일보다 **우리가 못 읽는 일이
              훨씬 흔합니다**(각 277~1,002건)
title · org_name · url · source  — 애초에 null 이 안 옵니다 (60일 0건)
```

★ **그래서 「가드 후보 8칸」은 넣는 쪽이 맞아 보입니다.** 다만 한꺼번에 넣으면
무엇이 달라졌는지 가려지지 않으므로, **칸기록을 한 주 보고** 그 칸이 실제로
지워지는지 숫자로 보고 넣는 것을 제안합니다 — 어제 「먼저 켜고 한 주 뒤 줄
수를 보고 정하기」와 같은 결입니다.

## 4. 왜 08:00 바퀴가 마감일을 null 로 보냈나 — **세중님 추정이 맞습니다**

> 「상세 20시간 건너뛰기(10-14) — 마감일을 상세에서만 읽는 사이트는 상세를
> 안 연 바퀴에 null 을 보냄. 그때 직군은 「창구가 그때 가린 직군을 돌려주게」
> 고쳤는데 마감일은 빠졌을 수 있음」

**코드가 그대로 말해 줍니다** (`collect-hosp.mjs` 440~465행 주석):

> ★ 그리고 **그때 가린 직군을 함께 받아 씁니다.** 처음 판은 id 만 받았는데,
> 상세를 건너뛴 공고의 직군이 **매 바퀴 다시 사라져** 보류함으로 갔습니다
> (회원 화면 39 → 34).

`건너뛸것` 은 `Map<id, 직군>` — **직군 하나만** 받습니다.

```js
const 건너뛸것 = new Map();      /* id → 그때 가린 직군 */
… for (const x of ((s||{})['건너뛸것']||[])) 건너뛸것.set(x.id, x['직군'] || '');
```

마감일·시각·인원·근무지·자격·연봉은 받지 않습니다. 그래서 상세를 건너뛴
바퀴에는 그 칸들이 **목록 값(없으면 null)** 으로 보내집니다.

**같은 뿌리를 직군에만 고치고 날짜 칸에는 안 고쳤습니다** (지침 6절 —
「기준을 고치면 같은 기준을 쓰는 곳을 전부 찾아 함께 고친다」).

### 고치는 두 길 — **가드가 더 라지합니다**

```
㉠ 창구가 칸을 다 돌려주게 한다     상세건너뛸공고() 가 {id, 직군, 마감일,
                                   시각, 인원, 근무지, 자격, 연봉} 을 주고
                                   수집기가 그것을 다시 보냄
㉡ 빈 값으로 덮지 않는다            **이미 했습니다** (②)
```

㉡이면 창구를 안 고쳐도 됩니다 — 수집기가 null 을 보내도 기존 값이 지켜집니다.
㉠은 같은 값을 받아 다시 보내는 왕복이고, 칸이 늘어날 때마다 두 곳을 고쳐야
합니다. **㉡ 하나로 뿌리가 막힙니다.**

★ 단 `job_group` 은 ㉠이 맞습니다(가드를 넣으면 재판정을 막으므로) — 그래서
그 칸만 이미 ㉠으로 돼 있는 것이 올바릅니다.
